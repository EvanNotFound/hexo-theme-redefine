## Getting Ready for Development

<div className="fd-steps [&_h3]:fd-step">

### Work from the repository root

Open the theme repository in your editor and run the commands below from its root directory. The repository uses pnpm `11.20.0` and Node.js 24.x.

### Install dependencies

```bash
pnpm install --frozen-lockfile
```

This installs dependencies for the theme, the local Hexo demo site in `dev/site`, and the docs workspace.

### Enable theme development mode

For a Hexo site using the theme source, set `developer.enable` to `true` in its `_config.redefine.yml` file. The local demo keeps this setting in `dev/site/_config.dev.yml`, which `pnpm dev` loads automatically.

```yaml
developer:
  enable: true
```

### Start the local demo site

```bash
pnpm dev
```

This resets the demo site's generated state, links the current theme source into
`dev/site/themes/redefine`, starts Hexo at `http://127.0.0.1:4000`, and watches
both browser JavaScript and CSS. esbuild writes an unminified development bundle
with source maps under `source/js/build/dev/`, while Tailwind recompiles
`styles/theme.css`. Refresh the browser manually after JavaScript changes; the
development command does not provide live reload.

</div>

## Demo Site And Deployment Modes

`dev/site/` is the canonical Redefine demo site for local development, PR
previews, branch previews, and the production demo. Keep demo posts, pages, and
site configuration there; the generated `dev/site/themes/redefine/` link and
`dev/site/public/` output are local or CI state.

`dev/site/_config.yml` contains Hexo site settings,
`dev/site/_config.redefine.yml` contains intentional demo theme overrides, and
`dev/site/_config.dev.yml` contains only the local development-mode override.
Test-only configuration lives under `tests/fixtures/`.

Local `pnpm dev` keeps theme developer mode enabled and uses checked-out theme
assets. CI disables developer mode before generating every deployed site. PR
and branch previews use checked-out assets with CDN disabled, while the
production demo preserves the configured versioned CDN behavior.

## Build and Reset

Run these commands from the repository root:

```bash
pnpm clean
pnpm build
pnpm test
pnpm check
```

- `pnpm clean` removes all root-owned generated theme assets and demo state.
- `pnpm build` creates all production CSS and browser JavaScript.
- `pnpm test` runs the Node.js test suite and its generated-site coverage.
- `pnpm check` is the canonical pre-PR theme validation command and runs the
  tests followed by the production build.

`pnpm dev` owns both CSS and JavaScript watching, so standalone watch commands
and build-helper commands are not documented here.

Do not edit generated files directly. Core and plugin CSS lives in
`source/css/build/`, and JavaScript lives in `source/js/build/`; these paths are
generated locally or in CI and are not committed. Edit the source files instead.
Runtime assets under `source/assets/` remain checked in.

The generated site loads only the configured light and dark code themes, only
the enabled supported comment system's stylesheet, and APlayer styles only when
APlayer is enabled. These optional assets remain under
`source/css/build/plugins/` instead of being bundled into the core CSS. Number
Flow is an application dependency emitted in a lazy JavaScript chunk and loaded
when footer runtime or toolbar reading percentage is enabled.

The theme style pipeline no longer contains Stylus, and the demo site no longer
depends on `hexo-renderer-stylus`. Published packages contain the native CSS and
Tailwind outputs required at runtime, so consuming Hexo sites do not need a
stylesheet renderer.

## Preview Release Notes

Version bumps and Git tag creation remain manual. Before pushing a matching
version tag, generate and check the bilingual release-note preview:

```bash
RELEASE_LLM_URL=... RELEASE_LLM_KEY=... pnpm release:notes -- v2.10.0
pnpm release:notes:check
```

The target tag may not exist yet. These commands only write the Git-ignored
`release-notes.md` at the repository root; they do not publish npm or CDN
assets and do not create a GitHub Release. Review the output before pushing the
matching version tag. CI builds the theme before creating the GitHub Release.
If OpenCode is unavailable or its output fails validation, CI uses GitHub
automatic release notes.

## Project Layout

- `styles/theme.css`: Core native CSS and Tailwind entry with explicit theme
  style imports.
- `styles/base/`: CSS variables, global rules, animations, and base rendered
  content styles.
- `styles/components/`: Theme component styles that require complex selectors
  or cannot be expressed entirely in templates.
- `styles/plugins/`: Separate optional styles for code themes, comment systems,
  and APlayer.
- `source/css/build/`: Generated core and plugin CSS; do not edit it directly.
- `source/assets/`: Checked-in runtime assets.
- `source/js/`: Browser-side JavaScript source.
- `scripts/`: Hexo generation-time Node scripts.
- `layout/`: Hexo templates. Required Hexo entry files stay at the root,
  reusable rendered fragments live in `layout/components/`, and route-owned
  markup lives in `layout/pages/`. Only cohesive multi-file families such as
  comments, home, and post use subdirectories.
- `dev/site/`: Local demo-site configuration, posts, pages, and fixtures.

## Customizing the Theme

Use Tailwind utilities for ordinary layout and appearance in theme-owned EJS or
script-generated markup, and extract repeated UI into templates or helpers.
Use Tailwind's default spacing and border-radius scales rather than defining
theme-specific replacements. Keep route dispatch explicit in
`layout/pages/router.ejs`; custom pages are selected by documented `template`
front matter.
Native CSS under `styles/base/`, `styles/components/`, or `styles/plugins/` owns
global rules, rendered content, complex selectors, and third-party markup. After
adding a native CSS file, import it explicitly from `styles/theme.css` or the
appropriate entry.

### Use the Canonical Numbered Color Foundation

- `--rd-background-100` and `--rd-background-200` are for primary and alternate
  page backgrounds.
- `--rd-gray-100`, `--rd-gray-200`, and `--rd-gray-300` are for default, hover,
  and active component backgrounds, respectively.
- `--rd-gray-400`, `--rd-gray-500`, and `--rd-gray-600` are for default, hover,
  and active component borders, respectively.
- `--rd-gray-700` and `--rd-gray-800` are for default and hover high-contrast
  component backgrounds.
- `--rd-gray-900` is for secondary text and icons; `--rd-gray-1000` is for
  primary text and icons.
- `--rd-gray-alpha-100` through `--rd-gray-alpha-1000` mirror the solid gray
  roles when transparency is required; `--rd-gray-alpha-400` remains the
  standard structural border and divider.
- `--rd-primary-text` is for text and icons on primary-colored fills.
- `--rd-shadow` remains the complete mode-aware shadow treatment.

Do not add component aliases such as `card` or `foreground`; components should
select the numbered variable that matches their role directly. Tailwind
mappings backed by color-mode or configuration-generated runtime variables
belong in `@theme inline`.

For more information, see the [official Tailwind CSS documentation](https://tailwindcss.com/docs).
